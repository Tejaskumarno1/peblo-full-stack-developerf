# Server changes that still need a database test

Commits `94ced39` and `c3f01da` (team authorization fixes) compile (`npm run build:server`) but have **never been run against a database**. Run these against a **local** Postgres named `peblo_test` (never `server/.env`, which points at production). `scripts/smoke-test.mjs` has one new check (sole-owner account deletion) that has not been run either.

1. **Sole owner cannot delete the account.** Create a user, make an organization, call `POST /auth/delete-account` and `/auth/schedule-deletion`: expect 409. Add a second active owner: expect 200. Set `deletion_requested_at` to 31 days ago for a sole owner and run `purgeScheduledDeletions`: the user must survive.
2. **Team note manage rights.** Team with A (author), B (member), C (lead). B gets 403 `owner_only` on DELETE, restore, archive, move, `PATCH {isArchived}` and `?permanent=1`. A and C succeed. Personal and Office behaviour is unchanged. Check the client toast text for `owner_only` and `no_access`.
3. **Join link.** `lookup` returns `ready`. Accept with `max_uses=1` from two concurrent requests: exactly one succeeds. Make `space_members` fail: `uses` is not burned. Set the org to `read_only`: `revoked`.
4. **Invite accept.** Accept twice at once: one 200, one 409 `state:'used'`. Revoke then accept: 409. Put a closed space and another org's space in `space_ids`: no `space_members` rows for them.
5. **`PUT /spaces/:id/members/:userId`.** Demote the only lead: 409. Make an org guest a lead: 400. Demote one of two leads: 200.
6. **Guest `GET /orgs/:id/members`.** Only name, avatar, role and status; only people sharing a space with the guest plus the guest; `invites` is `[]`. A non-guest gets the full list. Confirm the client does not break on missing `email` and `spaces`.
7. **Live edit after removal.** Remove a member who authored a team note: `/collab/ticket` returns 404 and the open socket closes. An author who is still a member keeps live edit in Team, Office and Personal.
8. **`spaceMembers()`.** Assign a task to an expired guest, a paused member and a member of a closed org: expect the "not in this space" 400.

Known gaps left on purpose: an invite to a `read_only` org still reads as `ready`; the guest member list does not exclude people who share only a closed space; check that a last owner can actually leave (the deletion message tells them to).

## Sharing, invites, export, mute and @mentions (branch feat-share, migrations 051 and 052)

Never run against `server/.env`. Use the local `peblo_test` database. `scripts/smoke-test.mjs` ends with a block "(added UNRUN) sharing, invites, export protection, mute, @mentions" that covers most of this; it has not been run. Two people O (owner) and M (member), both with a verified email, and a team T.

9. **Migrations.** Start the server on an empty `peblo_test`: 051 and 052 apply, `\d space_prefs`, `\d note_mentions` exist, `org_invites.last_reminded_at` exists. Start it a second time: nothing re-applies. Also check `_peblo_migrations` has versions 50 (`050_board_columns`), 51 and 52, and on a copy of a database that already has version 50 that 51 and 52 still run.
10. **Invites (R13).** O invites M (`POST /workspaces/orgs/:id/invites`): the returned `link` is `.../invite#token=...` (no `?token=`). M's notification (`GET /collab/notifications`, kind `org_invite`) has an empty body. As M, `GET /workspaces/invites/mine` lists it; with another verified user it lists nothing; with an unverified M it returns `verified:false`. `POST /invites/lookup {inviteId}` as M gives `ready`; as a different user gives `invalid`. `POST /invites/accept {inviteId}` joins (once; the second call is 409 `used`). Make an invite expire (`UPDATE org_invites SET expires_at = now() - interval '1 hour'`): `POST /invites/remind` returns 200 once and 429 the second time; the inviter gets ONE `invite_reminder` notification; after `last_reminded_at` is set 25 h back it works again. `POST /orgs/:id/invites/:inviteId/resend {mail:false}` returns a new link, the old token no longer looks up (`invalid`), the new one does; non-admins get 403; `audit_log` has `invite.link_copied`. With a configured mailer `{mail:true}` sends the email.
11. **Share policy (R9).** O makes a team note and `POST /share/note/:id` -> 201 (team notes could not be shared before). A viewer-role member gets 404 on that route and `GET /share/note/:id/allowed` says `read_only`; a writer who is not the author gets 201 on a normal team note but 404 when the note was shared to the team "can view". In an Office, a member without edit access gets 404. Create links on a note and a task in T, then `PATCH /spaces/T {publicLinks:false}`: both tokens are NULL in the database, `share_viewers/share_guests/share_settings` rows for them are gone, `GET /api/public/note/<old token>` is 404, a new link is 403 `team_off`, `audit_log` has `shares.revoked`. Turn it on, make links again, `PATCH /orgs/:id/policy {publicShares:false}`: the response has `revoked:{notes,tasks}`, every note/todo with a `space_id` in the organization has no token, audit has `policy.changed` and `shares.revoked`, new links are 403 `org_policy`, Personal links of the same people are untouched, and `GET /share/note/:id/allowed` says `org_policy`. Task-list links are intentionally not revoked.
12. **Export (R19).** `POST /orgs/:id/export` without password or with a wrong one: 403 (nothing in `audit_log`); wrong password 9 times in 15 min: 429. Right password as owner/admin: 200 JSON with `counts`; a plain member gets 403. `audit_log` has `org.exported` written even if you abort the download. Trashed notes are absent, present with `?includeTrash=1` (or body `includeTrash:true`). The 4th export within an hour: 429 `export_limit`. Seed 450 notes in a team: the file contains all 450 once each (chunks of 200), memory of the server stays flat; the old `GET /orgs/:id/export` is 404. Private Office notes are still withheld.
13. **Mute.** M `PUT /workspaces/spaces/T/prefs {muted:true}` (non-member: 404; non-boolean: 400). O posts an Office announcement or changes a task status in T: M gets no row in `user_notifications` and no `notifications_changed` socket event; other members still do. O assigns a task to M: M still gets `assigned`. A comment on a task that @mentions M (kind `mention`): M still gets it. Unmute: notifications arrive again. Muting T does not affect another team.
14. **@mentions.** As O in T: `GET /workspaces/spaces/T/people-lite` lists M but not O (guests with an expired `guest_until` and paused members are absent). In an Office with a private note, `?noteId=` lists only people who can read it. `PATCH /notes/:id` with content containing `[@M](peblo-user:<M id>)`: exactly one `note_mention` for M, title "<O name> mentioned you in a note", body = the note title only (decrypt and check the text is not in it), `note_mentions` row exists. Saving again with the mention still there: no new notification; remove then re-add within 24 h: still none; set `notified_at` 25 h back and re-add: one more. A mention of O by O: none. A mention of a user who is not in the team, or who cannot read the Office note, or of a made-up id: none and no error. `POST /notes` with a mention in the body notifies too. A Personal note (no space) never notifies. Save through `collab:true` also notifies; edits through the live socket or a public edit link do not (known gap).

Known gaps left on purpose: the public share page returns a mention's user id as stored; task-list links and Orbit/River note pages are not covered by the share policy UI; a team switch or policy change does not tell the people whose link was revoked.
